# Validate wide objects through a temporary index above 40 members

<a id="adr-0009"></a>

- **Decision.** Runtime contract validation searches names with string-specific comparisons for objects of at most 40 input members and builds a temporary dictionary above that bound. A direct check of the first 32 members rejects an early name failure before the dictionary is built. The cutoff is an internal CPU and allocation compromise, not an admission limit.
- **Rationale.** Repeated list scans for allowed names, duplicates and property lookup grew much faster than object width. Accepted values, member order, first-error paths and original-value identity must not change. The index trades temporary allocation for CPU on wide valid objects.
- **Alternatives.** Scanning at every width keeps allocation low and leaves 500-field validation in the millisecond range. Indexing every object adds a dictionary to small objects that the string-specific search already serves. A retained cache, validation plan or public switch adds lifecycle and configuration without a consumer that needs them.
- **Consequences.** The dictionary checks names in input order and values in normalized schema order, distinguishes an absent property from a present null, and is discarded after each validation. Indexing allocates more than the improved linear search for wide valid objects, so lower allocation per call does not establish lower peak memory. Some failures after the early-name prefix still pay dictionary setup. Validation keeps no independent time, depth, width or allocation quota.
- **Evidence.** Median microseconds per operation, three fresh VMs per target, before and after: a 100-field object takes 280.41 and then 69.55 on Erlang and 1,909.65 and then 210.28 on Node; a 500-field object takes 6,763.64 and then 369.66 on Erlang and 53,468.94 and then 1,099.52 on Node. Typed and generated order controls stay within run-to-run variation. A replay of 58,936 inputs per runtime compared validation, encoding, decoding and rendered-JSON outcomes with the baseline and found no difference.
