# Retain benchmark observations as non-asserting evidence

<a id="adr-0010"></a>

- **Decision.** Benchmarks are observations of named local checkouts. No timing threshold enters a test gate, and no published performance claim derives from them. [BENCHMARKS.md](../BENCHMARKS.md) retains each capture as a dated section with its method, environment, summary tables and limits; the summaries and provenance stay beside it under `docs/benchmarks/` as non-markdown data. A summary holds every VM median and its range, so raw per-run logs are not retained in the tree and remain in repository history at commit `c79211d`. The document and the [oracle](../ORACLE.md) cross-link, and the README and AGENTS.md link both.
- **Rationale.** Timings depend on machine, runtime, garbage collection and scheduling, so a threshold would fail for reasons unrelated to behavior. A finding that justified a design choice must stay readable, with its method and limits next to its numbers, after the capture directory is superseded. A dated document that labels every figure an observation does not claim currency. Semantic acceptance and cost are separate questions with separate evidence.
- **Alternatives.** A timing ceiling in the gate turns host variance into failures. Recording findings only in decision records drops the method and comparison tables a later capture needs to stay comparable. Discarding the findings loses the cost evidence behind ADR-0006, ADR-0008 and ADR-0009.
- **Method.** Each target starts three fresh VMs per capture. Each VM runs an untimed warmup and then timed batches, and a reported cell is the median of the VM medians with the minimum and maximum of those medians as its range. Cases run in a fixed order, all baseline VMs run before all changed VMs, and fixture construction, parsing and codec construction stay outside timed batches. Erlang runs with one scheduler; no CPU pinning or frequency control is applied, so small differences are not causal estimates.
- **Findings, symmetric contract encoding.** Before the object index of [ADR-0009](0009-index-object-validation-above-forty-members.md#adr-0009), validating on encode raised a 500-field string object from 0.322 ms to 7.021 ms on Erlang and from 0.210 ms to 46.961 ms on Node, a bounded-integer array of 10,000 elements from 1.48 ms to 2.15 ms on Erlang, and left the `AnySchema` case unchanged. Runtime validation is therefore not negligible for a schema without numeric refinements. A caller that already holds a `ValidatedValue` renders it with `contract.value` followed by `value.to_string` and validates once.
- **Findings, schema generation.** At 100 items, generated and handwritten native encoding cost 135.05 and 134.39 µs on Erlang and 1,882.75 and 1,830.32 µs on Node, with similar allocation, so generation supplies types and maintained codec source rather than speed. Constructing a generated codec costs 3.84 µs and 6.49 KiB on Erlang and 66.38 µs and an estimated 26.66 KiB on Node; retaining the codec keeps that cost out of conversion. Pure source generation takes 0.332 ms per module on Erlang and 0.820 ms on Node. A dynamic contract over prebuilt values often allocates less because it validates instead of constructing, which does not justify a second dynamic validation pass.
- **Findings, parsing.** The 2026-09-20 harness measured document parsing at 9,847 ns on Erlang/OTP 28 and 41,057 ns on Node 24.15.0, with 200 warmup calls and 1,000 timed calls and no distribution or machine record. A parsed array of 262,143 integers peaked near 42 MB of Erlang process heap and grew a Node heap by about 120 MB; the original record carries no run date, sample count or hardware. Both sets size inputs and are not baselines or heap quotas.
- **Consequences.** `scripts/benchmark.sh`, `scripts/contract_encoding_benchmark.py` and `scripts/schema_generation_benchmark.py` create a fresh evidence directory and refuse to reuse one. The weekly `Benchmark observations` workflow runs the harness on both targets. A new capture adds a dated section to BENCHMARKS.md instead of rewriting an older one, and an older section keeps its own stated limits. The package gate keeps the benchmark fixtures' semantic tests.

## Engine experiment retention, 2026-10-26

For the new parsing and generated-code engines, the owner selected a leaner
retention policy: design conclusions remain in ADRs 0014–0016, and maintained
benchmarks compare current implementations with vanilla parsers/codecs. Engine
prototypes, historical captures, archives and adoption reports are removed from
the checkout. This supersedes the per-capture retention policy above for those
experiments only. Existing schema, contract and object-validation observations
and all correctness oracles remain unchanged. Timing continues to be non-gating.
