# Hold each codec input once

<a id="adr-0018"></a>

- **Decision.** Every combinator stores one closure, a thunk that captures the combinator's inputs once (child codecs, the record continuation and getter, enum variants, bounds, caller callbacks) and builds the codec's operations each time the codec is used. A union variant stores one such thunk for its payload operations. A tagging function holds only its variant's identity, a runtime-unique integer; the tagged value carries its payload untyped until the union encodes it, finds the variant by that integer, and so knows the payload's type. Ordinary codecs also encode text directly: `encode_json` writes the bytes that rendering the encoded `Value` would write, and fails with the same errors.
- **Problem.** A BEAM process copy does not preserve sharing. Up to 2.1.1 a codec was a record of closures and each combinator stored several closures over the same inputs: a record field held its continuation in twelve references and a string enum its labels in five. A copied codec cost many times its in-heap size (an application's agent 289 kB flat against 19 kB in-heap, a run-time enum label about 1 kB), and in 2.0 and 2.1.0 the cost multiplied per nesting layer until a consumer VM ran out of memory. The [codec practice guide](../CODEC-PRACTICE.md) could not remove a codec captured by a later field, and its run-time enum rule rebuilt and re-validated the enum on every conversion.
- **Promise.** A codec's flat size equals its in-heap size apart from sharing inside the caller's own values: the library adds no duplication, a value captured by a continuation is copied once, and a run-time label costs its own data once. This holds for every later 2.x release. Copy-size tests check it for every public combinator, and a completeness check fails when a combinator has none.
- **Rules that follow.** A thunk body builds operations and nothing else; data derived from inputs, such as an enum's label list, is computed inside the operation that needs it. A codec keeps no cache: anything derived and kept would be held beside its inputs. Operations are rebuilt per use, so conversion allocates somewhat more short-lived memory than 2.1.1.
- **Behavior.** Results, errors, paths, schemas, placeholders, definition errors and the order and number of user callbacks are as in 2.1.1, except for two union cases. A value tagged by a tagging function from another `codec.union` block panics when encoded, with a message naming the encoding union's tags; 2.1.1 encoded it with the other union's payload codec, and `check` cannot see it. A union payload is encoded after `match` returns, for the returned value only, so a `match` that calls several tagging functions, or works after calling one, sees payload encode callbacks later or not at all. A scan of every consumer found neither. Outside the 2.x contract, `==` between separately built codecs containing a union becomes false on Erlang, and stack frames naming library functions change.
- **Rationale.** One stored closure per input gives the copy promise while keeping each combinator's operations together and typed, as in 2.1.1, so the compiler still checks the internals; only the union payload passes through one coercion, guarded by the variant's integer. A tagging function that held its payload codec would hold every payload twice, so nested unions would copy at 2^depth. A small integer is an immediate term, so a variant and its tagging function share it without copying it twice.
- **Alternatives.** An untyped data tree (one node per combinator and an interpreter per operation) copied the same, ran 1.1–2.0× faster and allocated 20–70% less, but its interpreters escape the compiler and spread each record's behavior over about thirteen functions; it stays the documented fallback if more speed is needed. A typed closure dispatching on an operation sum type was slower than both. Building a union on each use removed both union exceptions but ran 1.7–1.9× slower and allocated 3.6–4.4× more on union-heavy conversion. Keeping several closures per combinator with smaller captures (2.1.1, and passing the field record to field operations) still copies each input once per holder. Generation by default cannot express run-time enums or unions. Pipe builders were rejected by [ADR-0004](0004-continuation-records-and-definition-errors.md#adr-0004), whose builder and definition-error decisions this ADR keeps. A `persistent_term` registry or run-time compiled codec modules need global GC or code purges and have no JavaScript form.
- **Amends.** [ADR-0016](0016-specialize-generated-codecs-with-runtime-semantics.md#adr-0016) reserved specialized text encoding to generated codecs and recorded that ordinary composition keeps Value encoding. Ordinary codecs now also encode text directly, under the same byte- and error-equality to the Value render; generated codecs keep their own text encoders.
- **Consequences.** A minor release, 2.2.0; public signatures are unchanged. Consumers with a minimum below 2.2.0 keep the guide's copy rules; with a minimum of 2.2.0 they are no longer needed. The copy-size tests are valid for Erlang/OTP 29 on 64-bit and are re-baselined if an OTP release changes term layout. The two pending rulings on record continuations and on schema-generated children are closed: a child codec bound before a field chain is held once like any other input.
- **Evidence.** A spike on the 2.1.1 sources passed the root suites on both targets, a differential probe of every public operation and user-callback trace byte-identical to 2.1.1 on both targets, and byte-identical consumer payloads and schemas; flat sizes fell 9–74× on consumer shapes with conversion times at parity. The dated observations are in [BENCHMARKS](../BENCHMARKS.md).
