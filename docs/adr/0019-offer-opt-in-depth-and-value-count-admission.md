# Offer opt-in depth and value-count admission

<a id="adr-0019"></a>

- **Decision.** `value.Limits` gains two optional bounds, set with `value.with_max_depth` and `value.with_max_values`. A document nested deeper, or holding more values, fails with `DepthLimitExceeded` or `ValueLimitExceeded`. `value.default_limits()` leaves both unset, so default admission stays byte-only and existing callers are unaffected. The documented setting for input from an untrusted peer is a depth of 128 and 262,144 values.
- **Amends.** [ADR-0014](0014-adopt-native-erlang-decoding-with-byte-admission.md#adr-0014) removed global depth and value-count limits because the prototypes needed another traversal to enforce them. Its default, byte-only admission, stands. This record adds bounds a caller chooses, enforced without another traversal on Erlang.
- **Problem.** A byte bound does not bound nesting. A 1 MiB document can nest about 500,000 levels. Every function that walks a parsed value recurses once per level, so each consumer had to write its own depth check over the decoded tree before calling any of them, and on JavaScript deep nesting exhausts the host stack inside those functions, where it is thrown and not returned.
- **Mechanism.** On Erlang the OTP decoder threads an accumulator through its container callbacks; the bounded path carries the depth and a running value count in it and checks them in the callbacks that already run for every container and member. On JavaScript a scan of the text counts open brackets outside strings before `JSON.parse`, and the reviver, which `JSON.parse` already calls once per value, counts values. With neither bound set, both targets run the unchanged byte-only path.
- **Why not a default.** A finite default would refuse documents that 2.x admits today, which is a breaking change, and ADR-0014 records byte-only admission as the owner's choice. Making the bounds default belongs to a major release and a separate decision.
- **Consequences.** `ParseReason` gains two variants; its documentation already asks callers to match with a `_` branch. `is_limit_exceeded` is true for them. `with_max_bytes` keeps the other bounds of the limits it is given. On Erlang a refused document is still parsed to its end, because syntax admission completes first, but nothing is retained inside a refused container. On JavaScript the depth scan runs before the parser, so a document that is both malformed and too deep reports the depth bound there and the syntax error on Erlang. When a document exceeds both bounds, the reported one can differ by target.
- **Cost.** The [dated observations](../BENCHMARKS.md#structural-admission-bounds-2026-11-24) give every row. With both bounds set, Erlang parsing took about the same time on a flat array of integers, about a third longer on 15,000 small records and about two thirds longer on a document made only of nested arrays. On Node the difference was inside the run-to-run range.
